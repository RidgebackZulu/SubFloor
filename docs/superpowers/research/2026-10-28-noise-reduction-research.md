# Noise reduction for weak HF SSB voice (HFGCS 11.175 USB) in SubFloor

Date of research: 2026-10-28. Target: Swift 6 / SwiftUI, macOS 15+, Apple Silicon, 48 kHz mono float after AGC, live and file playback, one control (Off + strength), tens of ms latency, modest CPU, closed or permissive licensing.

Evidence grades used below: [P] primary source (source code, vendor/author page, paper), [A] anecdotal (forum/operator opinion), [M] I measured it myself on this Mac (macOS 26.6.2, Xcode SDK), [K] from my background knowledge, not re-fetched this session.

## 0. Executive summary

1. Best fit: write an in-house Swift/Accelerate spectral NR: MMSE log-spectral-amplitude (LSA / OM-LSA) gain with decision-directed a priori SNR and MCRA or minimum-statistics noise tracking, band-limited to the SSB passband, with a gain floor as the strength control. This is the same family as WDSP NR2 (EMNR), SDR Console NR5/Ephraim-Malah, ClearQSO "AI Engine 1" and AetherSDR's macOS-only MNR (which is exactly this, on Accelerate). Permissive license (it is your code), about 0.3 ms per 10.7 ms hop on M-series (AetherSDR's number), 11 to 32 ms latency, identical code path for live and files.
2. Optional "AI" tier: DeepFilterNet3 (MIT/Apache-2.0) via a Core ML streaming port (30 ms fixed delay, about 0.26 ms compute per 10 ms hop). Best neural option that is license-clean on macOS. Must be blended (dry/wet) and ideally faded out as SNR rises, because it was trained on microphone noise.
3. Cheap/robust neural alternative: RNNoise (BSD-3-Clause), plain C via SwiftPM, 10 ms frames, tiny CPU. Handles static crashes well per one vendor, but its band layout is wrong for a 300-2700 Hz passband.
4. Do not use Apple AUSoundIsolation for this. I tested it on this machine: it loads on arbitrary 48 kHz mono float streams, but it is a binary voice/not-voice gate. On synthetic weak SSB it muted about half the speech frames at -3 dB in-band SNR and muted everything at -9 dB; the "HighQualityVoice" model passes the noise through instead. Latency is 56 ms (Voice) or 92 ms (HighQuality).
5. Most on-target but GPL: WDSP 2.10 NNR (Sept 2026), trained on off-air HF noise and speech passed through an SSB transmit chain. GPL v2+, so only usable if SubFloor itself becomes GPL. Also worth keeping in mind as a quality yardstick (Thetis/piHPSDR/AetherSDR users can A/B against it).
6. LGPL flag: libspecbleach (NR4) is LGPL-2.1-or-later. GPL flag: all of WDSP (NR, NR2, NR3 glue, NNR). BSD/MIT/Apache: RNNoise, DeepFilterNet, Speex DSP preprocessor (BSD-style, verify COPYING), WebRTC NS (BSD-3, [K]).
7. A combination is worth it only in one form: a light spectral NR stage that is always the base, plus an optional neural stage run at reduced strength (ClearQSO does exactly this: neural engine plus the statistical engine at half strength after it). Do not stack two heavy stages.

## 1. What I measured myself (and its limits)

Setup (scratchpad, nothing in the repo touched): macOS 26.6.2, Xcode SDK headers, Python 3.10 + numpy. Test material: macOS `say -v Alex` speech (16 s, Skyking-style message), band-limited to 300-2700 Hz, plus Gaussian noise band-limited identically, at in-band SNR +3, -3, -9 dB, and a "crash" variant (-3 dB hiss + six 10 ms impulsive bursts at +18 dB). Processing: AUSoundIsolation through a real AudioUnit (AudioUnitRender, 512-frame slices), and a quick numpy reference implementation of spectral subtraction, Wiener (DD) and log-MMSE (DD) with a naive minimum-statistics noise tracker (not a polished MCRA, no whitening, no post-filter; a prototype).

Metrics: SI-SDR vs the clean reference (higher is better), a crude STOI-like band-envelope correlation (NOT real STOI; only for ranking), and gap RMS (level in clean-silent frames).

Results, SI-SDR in dB (input value in the "none" row):

| In-band SNR in | none | AU Voice | AU HQVoice | SpecSub | Wiener DD | log-MMSE DD (floor -18 dB) |
|---|---|---|---|---|---|---|
| +3 | 3.0 | 10.4 | 9.1 | 7.8 | 9.5 | 9.5 |
| -3 | -3.0 | 3.4 | 1.2 | 1.5 | 4.2 | 4.1 |
| -9 | -9.0 | -9.4 | -8.9 | -5.7 | -3.0 | -3.2 |
| -3 + crashes | -3.1 | 3.3 | 1.0 | 1.4 | 4.1 | 3.9 |

STOI-like at -9 dB: none 0.708, AU Voice 0.663 (worse than no processing), AU HQ 0.702, log-MMSE 0.724. At -3 dB: none 0.765, AU Voice 0.806, log-MMSE 0.799.

AUSoundIsolation behaviour on speech frames (median level change vs the noisy input): +3 dB in: -2.5 dB (4% of frames more than 10 dB down); -3 dB in: -9.8 dB median, 49% of speech frames more than 10 dB down; -9 dB in: -54 dB, 100% of frames gone (the unit outputs near-silence, gap RMS -46 dB). HighQualityVoice at -9 dB: nearly unchanged (noise left in, gap RMS +7 dB), at -3 dB gap RMS only -5.5 dB.

Strength mapping experiment on the reference log-MMSE (in = -3 dB): gain floor -6 dB gives SI-SDR 0.2; -10: 2.2; -14: 3.5; -18: 4.1; -24: 4.25 (plateau; STOI-like 0.786, 0.795, 0.798, 0.799, 0.799). Scaling the gain by exponent (G^0.5) was clearly worse (1.9 dB) than lowering the floor. So the gain floor is the effective strength knob, and returns diminish below about -18 dB.

Caveats you should weigh: (a) TTS speech is not real SSB speech and may look less speech-like to Apple's classifier; (b) Gaussian noise is easier than real HF noise (non-stationary, fading, crashes, heterodynes); (c) SI-SDR and my STOI-like proxy are not listening tests; (d) my numpy NR is a prototype, so its numbers are a floor, not a ceiling; (e) I did not run RNNoise, DeepFilterNet or libspecbleach locally (that needs downloading code/models, which I did not do without approval). The relative ordering (AU as a gate, classic MMSE gives a few dB) is the useful finding, not the absolute figures. A proper A/B on real HFGCS recordings is the thing to do next; the harness is at `.../scratchpad/au/` (auiso.swift, ev.py, ev2.py).

## 2. Apple built-ins

### AUSoundIsolation (kAudioUnitSubType_AUSoundIsolation)
- Facts from SDK headers [M/P]: Effect AU `aufx`, Apple manufacturer, "An audio unit that can be used to isolate a specified sound type". Parameters: `kAUSoundIsolationParam_WetDryMixPercent` (id 0, range -100..100 as reported by the unit, default 100) and `kAUSoundIsolationParam_SoundToIsolate` (id 1, 0 = HighQualityVoice [macOS 15+], 1 = Voice [macOS 13+, default]). That is all: no strength/aggressiveness control beyond wet/dry. Source: AudioUnitParameters.h in the Xcode SDK.
- Usable on arbitrary streams: yes. It is a normal effect AU; it did not care that the input was not a mic. Instantiate with AudioComponentFindNext/AudioComponentInstanceNew (or AVAudioUnitEffect), set 48 kHz mono non-interleaved Float32 on both scopes, render from a callback; worked first try (formats accepted, `AudioUnitInitialize` = 0, MaximumFramesPerSlice 4096). Rogue Amoeba ships it as a system-wide effect in SoundSource 5.6 ("any app"), and an Apple engineer on the dev forums calls it a public AU you can use in your own signal chain, independent of the system mic mode [P: weblog.rogueamoeba.com, developer.apple.com/forums/thread/829792].
- Latency [M]: reports kAudioUnitProperty_Latency 56.35 ms (2704 samples) for Voice; measured alignment lag 2704 samples (Voice) and 4440 samples = 92.5 ms (HighQuality). Independent of slice size (512 vs 4800 gave the same SI-SDR).
- CPU [M]: about 1.5% real-time factor in my offline loop (0.25 s wall for 15.9 s audio), i.e. cheap.
- Quality on weak SSB [M]: poor; see section 1. The Voice model is a speech presence gate trained for microphone/background-noise isolation; once in-band SNR gets to about -3 dB it chops speech, at about -9 dB it deletes it. HighQuality is more conservative and just lets noise through. Strength is only wet/dry mix (so 50% mix gives a half-level voice and half-level noise with the time-varying gating still in it). This is exactly the "gating speech" failure mode.
- Caveats: macOS 13+ (HighQuality macOS 15+); behavior across macOS releases is not guaranteed (closed, opaque model); some hosts report it does not load (Audacity forum thread: forum.audacityteam.org/t/in-stall-leaves-out-plugins/75426); no way to tune it to the 300-2700 Hz passband.
- Verdict: do not use as the main NR. Might be offered later as an experimental "voice isolate" for very strong, clean signals only; low priority.

### Other Apple frameworks
- Voice processing (AVAudioEngine `setVoiceProcessingEnabled`, kAudioUnitSubType_VoiceProcessingIO, `AUVoiceIO`): microphone-chain only (AEC, AGC, NS tied to the I/O unit). Not usable for a software stream. [K]
- Accelerate (vDSP FFT, vForce, BNNS) and Core ML: the building blocks for an in-house spectral NR (vDSP) and for running DeepFilterNet (Core ML). AetherSDR's MNR proves the Accelerate route [P].
- SoundAnalysis / Speech / SpeechAnalyzer: classification and transcription, not enhancement. AUDynamicsProcessor / AUNBandEQ are useful for gate/EQ post-shaping only. [K]
- I found no Apple API that does classical or neural denoising of arbitrary streams other than AUSoundIsolation.

## 3. Classic DSP

General facts (all [K] unless cited): STFT frames 20-32 ms with 50-75% overlap; analysis/synthesis sqrt-Hann; latency about one frame (10-32 ms); CPU trivial (well under 1% of a core with vDSP).

- Spectral subtraction (Boll 1979): subtract an over-weighted noise estimate from the magnitude spectrum. Simple, but strong "musical noise" (isolated tonal blips) and speech distortion at low SNR; improved by multi-band over-subtraction and spectral floor. In my test it was the weakest classic method at -3 dB (SI-SDR +4.5 dB gain vs +7.2 for Wiener/log-MMSE).
- Wiener filter with decision-directed (DD) a priori SNR: gain xi/(1+xi); smooth and cheap; slightly less aggressive on musical noise than SS; it performed essentially equal to log-MMSE in my test.
- MMSE-STSA (Ephraim-Malah 1984) and log-MMSE / MMSE-LSA (Ephraim-Malah 1985) with DD a priori SNR: Cappé (1994) showed the DD smoothing (alpha about 0.98) is what suppresses musical noise, at the price of a one-frame lag in SNR and some onset smearing. Hu and Loizou's listening study (13 algorithms, ITU-T P.835) is the standard comparison; statistical-model methods (MMSE family) are generally rated among the best at quality [P: pmc.ncbi.nlm.nih.gov/articles/PMC2098693; "ranked best" not verified by me]. WDSP's EMNR implements MMSE-STSA/LSA gain with DD, plus Pratt's "trained" lookup tables and optional AEPF (frequency-smoothing post filter) [P: emnr.c].
- Noise estimation: minimum statistics (Martin 2001, optimal smoothing, bias compensation; a 1.5 s tracking window typical), MCRA/IMCRA (Cohen 2003, speech-presence-probability recursive averaging), MMSE-based tracking (Gerkmann and Hendriks 2012; SPP-MMSE used in libspecbleach). WDSP implements LambdaD (min-stats style) and LambdaDs (MCRA-style) and a newer NSTAT method [P: emnr.c, WDSP changelog]. For HF hiss that is quasi-stationary over seconds this works; crashes and fading make the estimate chase the wrong thing, so use an impulse blanker upstream and long-ish tracking windows.
- OM-LSA with MCRA (Cohen and Berdugo): the ClearQSO "AI Engine 1" [P: clearqso.com]. This is the strongest "classic" variant for non-stationary noise and is what I would implement.
- Intelligibility caveat (important for a "weak voice" goal): enhancement algorithms generally improve quality but not intelligibility; Loizou and Kim (2011) attribute the failure to amplification distortions larger than about 6 dB (attenuation distortion matters little) and show that controlling these distortions yields large intelligibility gains even for spectral subtraction [P: pmc.ncbi.nlm.nih.gov/articles/PMC3169296]. Practical rules: gain never above 1, a gain floor (do not fully gate), no abrupt per-bin gain changes, protect speech onsets. The DD estimator plus a -15 to -20 dB floor satisfies these.
- LMS adaptive line enhancer (the old ham "NR"; WDSP ANR; Widrow 1975): a delayed-input predictor that keeps correlated (periodic) components and discards uncorrelated hiss. Great for CW and steady tones, but speech is only quasi-periodic with short, varying correlation time, so on voice it needs delicate delay/step-size tuning and gives a "watery/ringing" sound and weaker gains. This is my inference supported by ALE theory [A/K: general ALE sources e.g. eit.lth.se ALE reports]; frequency-domain ALE variants reduce harmonic damage. Not recommended for SubFloor's voice goal, except possibly as a narrow ANF/notch for carriers.
- Two-step / TSNR (Plapous, Marro, Scalart 2006): refines the DD estimate to remove frame lag; reduces residual musical noise, can cause some harmonic distortion at low SNR [P: cairn.enssat.fr/bindocs/publications/Scalart04.pdf and PLAPOUSICASSP2005.pdf]. Optional refinement.

## 4. What SDR software actually ships (and operator reports)

Hard fact: I found no controlled listening test or published ranking of these NRs on weak SSB. Everything below about "rated best" is forum anecdote. Treat it as directional.

- WDSP (Thetis, piHPSDR, deskHPSDR, AetherSDR, Kainos): GPL v2+ [P: emnr.c header "GPL v2 or any later version", Warren Pratt NR0V]. Modes: NR (LMS ANR), NR2 (EMNR, spectral MMSE with DD, noise estimators, optional trained gain, AEPF, psychoacoustic post-processing since 1.27), NR3 (RNNoise glue), NR4 (libspecbleach), and in WDSP 2.10 (2026-09) NNR (neural). Operator reports: NR2 is the one most often praised for weak SSB: users say it can pull voice from hiss without burying it the way some radio-side NRs do, "trained" mode in particular; drawbacks: it colors the audio, and on weak signals the T1/T2 thresholds must be set correctly or voice is cut [A: community.apache-labs.com threads p=24055, 17607 search snippets]. NR4 got an "amazing on SSB" one-liner, with 0-20 dB adjustable reduction [A]. NR3 has no tuning parameters in Thetis [P: github.com/ramdor/Thetis/discussions/585].
- WDSP NNR (Standard 262k params / Premium 585k params, 16 kHz internal, 512-point STFT, conv+recurrent+deep-filter stages, GPL, compiled-in weights; trained on off-air HF noise recordings with speech passed through a real SSB transmit chain; +4.3 / +4.9 dB SDR on 8 held-out recordings per the author's guide; about 10% / 32% of one thread on a 9950X3D; about 51 ms added delay vs 64 ms for EMNR; blocked in CW/digital because it removes steady tones) [P: github.com/aethersdr/AetherSDR/issues/5684; github.com/custosonlinux/pihpsdr-nnr-patch; github.com/trininfo/wdsp changelog]. Kainos reports about 15% (Standard) / 35% (Large) of one core, about 50 ms delay, speech in white noise: pauses reduced about 25 dB, speech nearly unchanged [P: github.com/PNWHam-K7JUS/Kainos/releases/tag/kainos-1.0.13]. The author claims it beats DeepFilterNet3 and RNNoise but no independent operator verdict yet (the AetherSDR issue contained no operator feedback). This is the single most relevant design for SubFloor's problem, and its architecture/training recipe (HF noise + SSB chain simulation) is a template.
- AetherSDR (FlexRadio client, Qt6, Linux/macOS/Windows): seven methods: NR2, RN2 (RNNoise), NR4, NNR, DFNR (DeepFilterNet3, prebuilt lib), MNR (macOS-only: decision-directed MMSE-Wiener, 512-point real FFT at 24 kHz, 50% overlap, sqrt-Hann, noise floor by minimum statistics over 25 frames, per-bin temporal gain smoothing to suppress musical noise, Accelerate vDSP/AMX, about 0.3 ms per hop, one hop (10.7 ms) latency, strength slider 0-100), BNR (NVIDIA GPU) [P: github.com/ten9876/AetherSDR/releases/tag/v0.8.19]. Direct existence proof that the recommended in-house design is practical on exactly your platform.
- SDR Console (Simon Brown): several NRs; one user calls the Ephraim-Malah one "very effective on noisy SSB", another says NR5 gives the best results; some settings produce "burbling" more annoying than the noise; NR does not rescue inaudible signals, it makes audible ones comfortable [A: fallows.ca SDR Console v3 post; forum.sdr-radio.com/viewtopic.php?p=11692]. A neural NR "based on the RNNoise paper" was in private beta (2019) [P: rtl-sdr.com]; later "RadioClear AI": two-stage (DSP noise estimate + harmonic analysis + adaptive spectral suppressor, then a 2-layer GRU, about 568k params, 8 kHz processing rate, 40 bands interpolated to 257 bins, 3-tap complex filter, trained on speech + real receiver noise at +15 to -10 dB SNR), claimed "cleaner background noise and natural-sounding speech than RNNoise" in subjective tests, with an aggressiveness control; controlled comparisons "still needed" [P: sdr-radio.com/new-noise-reduction as summarized].
- SDRuno / SDRconnect (SDRplay, closed): SDRuno NR reported by users to make weak SSB readable that is not intelligible with NR off (e.g. about -119 dBm) [A: sdrplay.com/community]. SDRconnect NR is a different, lighter design and "will not pull very weak signals out of high background noise" per SDRplay's own note [P-ish: search summary of SDRconnectNBNRappnote.pdf; PDF itself returned 404 when I fetched it]. Closed source: no integration route.
- SDR#: IF and audio NR plugins (Airspy, closed); a 2019 update with a smoothing algorithm using ideas from the RNNoise paper gave "noticeably less hiss and slightly clearer" at the same threshold [P: rtl-sdr.com]. 
- SDR++: only an IF noise reduction (NFM/WFM only) and a noise blanker (USB/LSB/DSB) in the radio module; no spectral audio NR for SSB that I could confirm [P: sdrpp.org/manual.pdf via search; moderately confident].
- GQRX: noise blanker (and no spectral NR that I could find). SDRangel: no NR found in the SSB demodulator in my search (SSB demod has AGC and filter controls) [moderate confidence; absence of evidence].
- ClearQSO (VU3RAZ, Windows, free for hams; uses RNNoise BSD and DeepFilterNet3 MIT/Apache): three engines: 1 = OM-LSA with MCRA (statistical, lowest delay, strong/medium signals), 2 = RNNoise-based (handles static crashes, barely any CPU), 3 = DeepFilterNet3 (strongest on weak noisy signals, about 40 ms delay); for engines 2/3 the OM-LSA engine also runs afterward at half strength; AUTO fades the AI back as SNR rises about 8 to 20 dB because neural engines trained on microphone speech color strong SSB. Vendor STOI benchmark on a synthetic SSB contact (3 voices, 300-2700 Hz, fading, noise, crashes), all at 60% strength: raw 0.57 / 0.48 / 0.46 at 0 dB / -6 dB / 0 dB+static; Engine 1: 0.60 / 0.49 / 0.50; Engine 2: 0.60 / 0.50 / 0.55; Engine 3: 0.62 / 0.51 / 0.55 [P: clearqso.com; vendor-run, offline, synthetic]. Takeaway: at weak SNR all methods give small STOI gains (+0.02 to +0.05 at 0 dB; +0.01 to +0.03 at -6 dB); neural helps most when crashes are present (+0.05 to +0.09).
- Hams on RNNoise: OERadio claims S3-S4 SSB becomes clearly intelligible where classic NR yields artefacts (no data) [A]; AetherSDR RFC argues RNNoise/DFN spend capacity above 4 kHz that an SSB passband does not carry and were not trained on HF phenomena (crashes, mistuning, Watterson fading, AGC) but reports no measured failure [P: github.com/aethersdr/AetherSDR/issues/6346].

## 5. ML candidates in detail

### RNNoise (Xiph)
- Hybrid: classic DSP framework (22 Bark-like bands, pitch filter) + small GRU net that predicts per-band gains. 48 kHz, 480-sample (10 ms) frames, about 10 ms algorithmic latency [K for frame size; xiph/rnnoise README gives 48 kHz mono 16-bit PCM]. Trained on public datasets; "little" model variant exists in v0.2 [P: github.com/xiph/rnnoise].
- License: BSD-3-Clause [P]. Plain C, autotools build (CMake/Meson ports exist; SwiftPM with a C target is easy). Model weights compiled into rnnoise_data.c, no runtime deps.
- CPU: very low (about 1% of a core or less on Apple Silicon [K]; Mozilla: "runs easily on a Raspberry Pi" [P]).
- Behavior on SSB: designed for mic speech in office/street noise; gain bands span 0-24 kHz so only a few bands cover 300-2700 Hz (coarse frequency resolution; cannot track voice harmonics), expects speech above 4 kHz that SSB lacks, so it can mis-classify band-limited voice. Known artifacts: metallic/underwater at high suppression, gating of weak/breathy speech; frame-wise gain jumps produce chopping on fluctuating weak signals [P: Shotcut docs; A/K]. Strength: there is no native strength parameter; implement as wet/dry mix and/or floor on per-band gains (RNNoise API gives only the VAD probability and processes in place, so a mix is the practical knob; Shotcut's "suppression" slider is a mix). ClearQSO ran it at 60-70% [P].
- Integration: C via SwiftPM, run in the render callback (real-time safe, no allocations). Must resample 48 kHz audio is already the native rate, so no resampling. 10 ms hop alignment: use a 480-sample FIFO.

### DeepFilterNet (DFN2/DFN3, Rikorose)
- License MIT or Apache-2.0 (dual) [P: github.com/Rikorose/DeepFilterNet]. DFN3: 48 kHz full band, 20 ms window, 10 ms hop, 2-frame lookahead = 40 ms latency in the paper; single-thread RTF 0.19 on a notebook i5-8250U [P: arxiv.org/abs/2305.08227]; about 2.17M params. Combines ERB-band gains (coarse) for stationary noise with "deep filtering" (complex FIR per low-frequency bin up to about 5 kHz) which models phase and speech harmonics: far better than RNNoise for natural sound at moderate SNR.
- Core ML ports: kylehowells' streaming Core ML (stateful, one 10 ms hop per call, 480 samples, fixed 30 ms algorithmic delay, about 0.26 ms Core ML compute per hop, 34.9x realtime on Apple Silicon, Apache-2.0/MIT, Swift API `DeepFilterNetCoreMLStreamer.processHop`) [P: huggingface.co/iky1e/DeepFilterNet3-Streaming-CoreML; Swift runtime in kylehowells/DeepFilterNet-mlx, not inspected by me]; aufklarer's FP16 about 4 MB model, RTF 0.12-0.24 on M2 Max, STFT/ERB on Accelerate [P: huggingface.co/aufklarer/DeepFilterNet3-CoreML]. Rust libdf/tract route also exists (the LADSPA plugin) but is heavier to integrate.
- Behavior on SSB: not specifically documented. Trained on DNS-challenge style office/street noise at 48 kHz [P: aethersdr issue 6346]. On the published ClearQSO benchmark it was the best engine at weak SNR and with crashes, but gains over the OM-LSA engine are small (0.62 vs 0.60 STOI at 0 dB). Known concern with any speech-trained NN at very low SNR: gains in intelligibility vanish (ΔSTOI near zero for a hearing-aid DNN at low SNR) and speech can be gated or "hallucinated" into formant-like noise [P: arxiv.org/pdf/1805.01198]. ClearQSO fades it out above about 8-20 dB SNR because it colors strong SSB [P].
- Integration: Core ML on a background thread with a ring buffer (Core ML prediction is not real-time-safe; 0.26 ms compute per 10 ms hop leaves lots of headroom, so a worker thread feeding a small output FIFO is fine, adds one hop plus 30 ms). Bundle the .mlpackage; avoid the default loader that downloads via swift-huggingface (use `.bundle`). Offline files: just iterate hops faster than real time (35x).
- Strength mapping: wet/dry blend of dry and processed (equal-latency aligned), possibly in the log-gain domain (apply G^s on the output spectrum is not possible with a black-box audio-in/audio-out model, so use a time-domain mix, or run the model, then apply a floor via the same STFT-domain "gain = |Y|/|X| clipped to [floor,1]" trick: compute the effective gain from model output vs input per bin, clamp to floor, smooth, re-apply to the input; this ensures the neural stage can only attenuate, never add content, and gives a floor-based strength like the classic stage).

### WDSP NNR / RadioClear AI / AetherN3R (HF-trained neural NRs)
See section 4. These are the only models trained for this domain. NNR (GPL, weights compiled in, C) cannot be used in closed code. RadioClear is closed. AetherN3R is only an RFC [P: issue 6346] (no published weights). Writing your own HF-specific small model (GTCRN-class: 48k params, 33 MMACs/s, ICASSP 2024 [P: github.com/Xiaobin-Rong/gtcrn via search; verify license before use]) is possible but is a research project: you would need your own HF-noise + SSB-chain training data. Not for v1.

### Other small real-time models (not tested)
Speex DSP preprocessor (BSD-style, xiph/speexdsp, [K: MMSE-LSA family + VAD]; old, tuned for 8-16 kHz telephone speech; could be a quick trial because it is already a 300-3400 Hz design, license to verify in COPYING), WebRTC NS (BSD-3 [K]; Wiener-like, decent for stationary hiss), Microsoft NSNet2/DNS baseline (MIT [K]), DTLN (MIT [K]). None of these has HF evidence; all inferior to a well-tuned OM-LSA for stationary hiss in my judgment (unverified).

## 7. Recommended design for SubFloor

Ranking:

1. In-house OM-LSA/MMSE-LSA spectral NR in Swift + Accelerate (default).
   - Why: best evidence-to-risk ratio. It is the algorithm family operators actually rate for SSB (NR2/EMNR, Ephraim-Malah in SDR Console, MNR on macOS), it measured best of the classic methods in my test at every SNR, has no license issue, trivially real time, and the same class can run offline on files. You control artifacts (floor, DD alpha, smoothing, post-filter) and can tune against real HFGCS recordings.
   - Spec: process in the passband only: decimate to 16 kHz (or 24 kHz like MNR), 512-point real FFT, hop 128-256, sqrt-Hann, 50-75% OLA. Bins outside 250-3000 Hz get a fixed fixed attenuation (e.g. -20 dB) or are left to an optional band filter. Noise tracking: MCRA/IMCRA or min-stats with 1.5-2.5 s window (WDSP uses about 1.5 s) and bias compensation; freeze/slow the noise update during detected impulses; optional upstream impulse blanker (audio-domain, 1-4 ms look-ahead, replacing samples above k x median-absolute-level with interpolation) because crashes otherwise corrupt the estimator and AGC-ed audio makes them loud. A priori SNR: DD alpha 0.96-0.98 (consider TSNR). Gain: LSA with gain <= 1, floor g_min. Post: temporal smoothing and optional frequency smoothing (WDSP AEPF idea) on the gain; optional faint comfort noise at the floor.
   - Single control: s in [0,1] ("Off" at 0). Suggested mapping: floor_dB = -(2 + 18 s) (so s=1 -> -20 dB, my data shows plateau at about -18 dB), noise-estimate scale beta = 1.0 + 0.5 s (mild over-estimation at the top), DD alpha fixed 0.98, post-smoothing grows with s. Do not map strength to a gain exponent (worse in my test). Crossfade dry/wet only to avoid clicks when toggling, ramp s over 50-100 ms. Consider an "Auto" mode: scale s down when estimated SNR is high (as ClearQSO AUTO does) since NR only hurts strong signals.
   - Latency about 20-35 ms; CPU about 0.3 ms per hop.
2. DeepFilterNet3 via Core ML, as an optional "AI" mode (Settings: "Noise reduction engine: Classic / AI").
   - Why: strongest license-clean neural option, runs on Apple Silicon at tiny cost, best vendor benchmark on weak SNR and crashes, and 30 ms delay is within your budget. Risks: not trained for HF; may gate weak voice at -6 dB or lower; third-party Core ML conversion needs vetting; a model-download default must be avoided.
   - Map the same s to a blend: out = (1-s) dry + s ai at low end; above about s=0.6 additionally run the classic stage at half strength after it (ClearQSO's hybrid). Always clamp effective gain to >= floor to keep it attenuate-only. Run on a dedicated thread with a ring buffer; hop 480.
3. RNNoise (BSD) as the lightweight AI fallback.
   - Why: easiest to integrate (C via SwiftPM, real time safe), very low CPU, handles crashes well per ClearQSO's engine, but quality on band-limited SSB is the least certain of the three. Worth trying first as a quick prototype of "AI mode" before investing in Core ML, then replace with DFN3 if it sounds better on real recordings.
   - Not ranked because of license: libspecbleach NR4 (LGPL-2.1+), WDSP NR2/NNR (GPL). If SubFloor is or can become GPL-compatible, WDSP NNR is likely the best quality for this exact problem and should be benchmarked as the reference; and if LGPL is acceptable (dynamic framework, relinkable, source offered) NR4 is a cheap trial.
   - Not recommended: AUSoundIsolation (measured: deletes weak speech), LMS ALE (voice), plain spectral subtraction.

Is a combination worth it?
- Yes in one specific shape: statistical stage as base, optional neural stage on top at reduced strength, which both ClearQSO ("AI Engine 1 also runs afterward at half strength") and AetherSDR's NR menu (mutually exclusive, so they do not stack) show as the tension: stacking heavy stages compounds artifacts. A light pre-stage (floor -6 to -8 dB, i.e. roughly 3 to 4 dB SNR improvement) before the neural model can help the NN see a better SNR and protect against its chopping, but it also shifts the input distribution away from what the NN was trained on; test both orders on real recordings.
- An impulse noise blanker in front of everything is worth more than another NR stage for "occasional crashes". 
- Do not stack AUSoundIsolation behind anything.

Offline/file playback specifics:
- Same processor instance type. On open/seek: prime the noise estimator by running about 2 s of pre-roll (for files you can pre-scan the whole file once for a min-statistics noise profile, giving zero-lag convergence), compensate the fixed algorithmic latency by dropping the first N output samples, flush on end.
- Run in the existing playback render path, or pre-render to a cache for export. Because analysis is deterministic, the same file plays identically.
- Neural stage offline can run 30-35x real time.

Real-time engineering notes (Swift 6): process in an AVAudioSourceNode/AUAudioUnit render block with preallocated vDSP buffers (no Swift allocation, no actors/locks); keep parameters in an atomic or lock-free struct; smooth strength per-sample; Core ML on a separate Thread/DispatchQueue with real-time-ish priority and an SPSC ring buffer (e.g. a pre-sized TPCircularBuffer-style); expose reported latency for Auto-record/recording alignment (recordings should store un-processed audio and apply NR at playback so you can retune later; if NR is applied to the live feed, tell the recorder which tap to use).
